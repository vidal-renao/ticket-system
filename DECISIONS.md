# Architecture Decisions

## ADR-001: Next.js App Router on Vercel

Status: accepted. The product uses one TypeScript deployment surface for UI, server rendering, Route Handlers and cron-compatible functions.

## ADR-002: Supabase Auth and PostgreSQL RLS

Status: accepted with hardening. RLS is the database authorization boundary; service-role access is exceptional and must include explicit tenant predicates.

## ADR-003: Customer-only self-registration

Status: accepted. Public callers cannot create staff roles. Agents and managers are provisioned by an authenticated administrator until signed, expiring invitations are implemented.

## ADR-004: AI remains assistive

Status: accepted. AI may classify and draft, but customer-facing messages require human review. Optional PII scrubbing reduces disclosed data.

## ADR-005: Fail-closed operational endpoints

Status: accepted. Missing or weak webhook/cron/setup secrets disable the endpoint instead of bypassing authentication.

## ADR-006: Forward-only security migrations

Status: accepted. Production fixes are new idempotent migrations. Historical files are not treated as proof of applied database state.

## ADR-007: One ticket access policy

Status: accepted. Ticket access is derived from the authenticated profile and ticket row: customers are owner-scoped, agents are assignment-scoped, and managers/admins are organization-scoped. Query helpers and point mutations must reuse the same policy.

## ADR-008: Reopening resumes active work

Status: accepted. Reopening a terminal ticket transitions it to `in_progress`, clears terminal timestamps and starts a new resolution SLA window. It does not create a second first-response obligation.

## ADR-009: Preserve waiting reasons

Status: accepted. `pending_customer` and `pending_third_party` remain separate states in storage, domain mapping, operational filters and presentation. Neither state may silently disappear from active queues or SLA processing.

## ADR-010: Swiss operations control-room design

Status: accepted. The product uses semantic graphite, signal-blue, SLA-amber and mint tokens with a restrained pulse-line signature. Accessibility, responsive layout and reduced-motion behavior are release requirements.

## ADR-011: Administrator approval is separate from waiting states

Status: accepted. Agent completion creates a pending review decision without reusing `pending_customer` or `pending_third_party`. Only an administrator can approve work as resolved or request changes.

## ADR-012: Specialist routing fails safely

Status: accepted. Automatic routing selects only active agents with a matching category specialty/team and uses active workload as the tie-breaker. When no specialist matches, the ticket remains unassigned for administrator triage; it is never assigned to an unrelated agent.

## ADR-013: Administrator routing overrides automation

Status: accepted. Assignment, category and priority overrides are administrator-only. A manual routing decision locks automatic reassignment until an administrator explicitly changes it again.

## ADR-014: Operational deletion is recoverable

Status: accepted. Ticket cleanup in the application is an administrator-only, tenant-scoped soft deletion with audit evidence and restoration. Permanent destruction belongs to a separate retention process and is not exposed as a dashboard action.

## ADR-015: Public reference codes, customer type, and invitation-based onboarding

Status: accepted. Fulfills the "until signed, expiring invitations are implemented" gap left open by ADR-003.

- **Reference codes.** Every profile gets an immutable, server-generated `reference_code` in the form `VRE-<ROLECODE>-XXXX-XXXX`, where `ROLECODE` is `ADM`/`MGR`/`EMP`/`CUS`/`COM` derived from `role` (and `customer_type` for customers). The `XXXX-XXXX` suffix is 8 characters drawn from a 32-symbol crypto-random alphabet (Crockford-style, excluding `0/O` and `1/I`) via `pgcrypto.gen_random_bytes`, generated by a `BEFORE INSERT` trigger with a bounded collision-retry loop, never client- or admin-supplied. This is a distinct, deliberately non-sequential identifier from the pre-existing `profiles.employee_id` (`EMP-0001`-style, globally sequential, added by `migration_phase1_routing.sql`) — `employee_id` is left untouched; deprecating it is out of scope for this phase. A trigger blocks any `UPDATE` that changes a non-null `reference_code`, for every role including `service_role`.
- **Customer type.** `profiles.customer_type` (`individual` | `company`, nullable only for non-customer roles, `NOT NULL` and constrained for `role = 'customer'`) replaces the implicit assumption in `app/api/admin/users/route.ts` that every admin-created customer is a company. It is not self-service-editable (no column grant to `authenticated`); converting between individual and company later is an explicit, audited, service-role-only operation, not built in this phase.
- **Canonical tenant.** "Vidal Real Estate" is identified server-side only by `organizations.slug = 'vidal-real-estate'` (already `UNIQUE NOT NULL`), never by its mutable `name` and never by a UUID literal in frontend code. The two new admin onboarding routes (individual/company customer) resolve and assign this tenant server-side unconditionally; the browser cannot supply `organization_id`. The pre-existing self-service `/api/auth/register` `org_code` mechanism (client-supplied org UUID, server-validated against `is_active`) is left as-is — it already rejects anything but a real, active org row, and changing it is out of scope here.
- **Separate onboarding flows.** `CreateUserModal`'s single generic agent/customer toggle is replaced, for customers, by two independent routes, Zod schemas and API endpoints — individual vs. company — each imposing its own server-side `role`/`customer_type`/`organization_id`/`reference_code`. Agent/employee creation keeps using the existing modal/route unchanged.
- **Invitation, not admin-visible passwords.** The two new customer onboarding routes use `supabase.auth.admin.inviteUserByEmail`, letting Supabase's own configured mailer deliver the invite; the admin never sees a temporary password. The invite's `redirectTo` lands on the existing `/auth/callback`, then the existing `/settings` → `ChangePasswordForm` lets the invited user set their own password — no new "set initial password" page is built, reusing what already exists. Agent creation's existing direct-password flow (`app/api/admin/users/route.ts`) is unchanged in this phase.
- **Profile area.** Self-service profile management already exists at `/settings` (avatar upload, password change, role-specific fields) — extended in place rather than duplicated into a new `/dashboard/profile`, per the "don't duplicate existing flows" guardrail.
- **Logo storage.** A new `logos` Storage bucket mirrors the existing `avatars` bucket's proven pattern exactly (public read, folder-scoped RLS keyed to `auth.uid()`, one file per user) rather than introducing a new private/signed-URL mechanism — company logos carry the same sensitivity profile as avatars, and reusing an already-reviewed pattern was judged lower-risk than a new one.
