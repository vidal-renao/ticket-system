# Architecture Decisions

## ADR-001: Next.js App Router on Vercel

Status: accepted. The product uses one TypeScript deployment surface for UI, server rendering, Route Handlers and cron-compatible functions.

## ADR-002: Supabase Auth and PostgreSQL RLS

Status: accepted with hardening. RLS is the database authorization boundary; service-role access is exceptional and must include explicit tenant predicates.

## ADR-003: Customer-only self-registration

Status: accepted. Public callers cannot create staff roles. Agents and managers are provisioned by an authenticated administrator until signed, expiring invitations are implemented.

## ADR-004: AI remains assistive

Status: accepted. AI may classify and draft, but customer-facing messages require human review. Optional PII scrubbing reduces disclosed data.

## ADR-005: Fail-closed operational endpoints

Status: accepted. Missing or weak webhook/cron/setup secrets disable the endpoint instead of bypassing authentication.

## ADR-006: Forward-only security migrations

Status: accepted. Production fixes are new idempotent migrations. Historical files are not treated as proof of applied database state.

## ADR-007: One ticket access policy

Status: accepted. Ticket access is derived from the authenticated profile and ticket row: customers are owner-scoped, agents are assignment-scoped, and managers/admins are organization-scoped. Query helpers and point mutations must reuse the same policy.

## ADR-008: Reopening resumes active work

Status: accepted. Reopening a terminal ticket transitions it to `in_progress`, clears terminal timestamps and starts a new resolution SLA window. It does not create a second first-response obligation.

## ADR-009: Preserve waiting reasons

Status: accepted. `pending_customer` and `pending_third_party` remain separate states in storage, domain mapping, operational filters and presentation. Neither state may silently disappear from active queues or SLA processing.

## ADR-010: Swiss operations control-room design

Status: accepted. The product uses semantic graphite, signal-blue, SLA-amber and mint tokens with a restrained pulse-line signature. Accessibility, responsive layout and reduced-motion behavior are release requirements.

## ADR-011: Administrator approval is separate from waiting states

Status: accepted. Agent completion creates a pending review decision without reusing `pending_customer` or `pending_third_party`. Only an administrator can approve work as resolved or request changes.

## ADR-012: Specialist routing fails safely

Status: accepted. Automatic routing selects only active agents with a matching category specialty/team and uses active workload as the tie-breaker. When no specialist matches, the ticket remains unassigned for administrator triage; it is never assigned to an unrelated agent.

## ADR-013: Administrator routing overrides automation

Status: accepted. Assignment, category and priority overrides are administrator-only. A manual routing decision locks automatic reassignment until an administrator explicitly changes it again.

## ADR-014: Operational deletion is recoverable

Status: accepted. Ticket cleanup in the application is an administrator-only, tenant-scoped soft deletion with audit evidence and restoration. Permanent destruction belongs to a separate retention process and is not exposed as a dashboard action.

## ADR-015: Public reference codes, customer type, and invitation-based onboarding

Status: accepted. Fulfills the "until signed, expiring invitations are implemented" gap left open by ADR-003.

- **Reference codes.** Every profile gets an immutable, server-generated `reference_code` in the form `VRE-<ROLECODE>-XXXX-XXXX`, where `ROLECODE` is `ADM`/`MGR`/`EMP`/`CUS`/`COM` derived from `role` (and `customer_type` for customers). The `XXXX-XXXX` suffix is 8 characters drawn from a 32-symbol crypto-random alphabet (Crockford-style, excluding `0/O` and `1/I`) via `pgcrypto.gen_random_bytes`, generated by a `BEFORE INSERT` trigger with a bounded collision-retry loop, never client- or admin-supplied. This is a distinct, deliberately non-sequential identifier from the pre-existing `profiles.employee_id` (`EMP-0001`-style, globally sequential, added by `migration_phase1_routing.sql`) — `employee_id` is left untouched; deprecating it is out of scope for this phase. A trigger blocks any `UPDATE` that changes a non-null `reference_code`, for every role including `service_role`.
- **Customer type.** `profiles.customer_type` (`individual` | `company`, nullable only for non-customer roles, `NOT NULL` and constrained for `role = 'customer'`) replaces the implicit assumption in `app/api/admin/users/route.ts` that every admin-created customer is a company. It is not self-service-editable (no column grant to `authenticated`); converting between individual and company later is an explicit, audited, service-role-only operation, not built in this phase.
- **Canonical tenant.** "Vidal Real Estate" is identified server-side only by `organizations.slug = 'vidal-real-estate'` (already `UNIQUE NOT NULL`), never by its mutable `name` and never by a UUID literal in frontend code. The two new admin onboarding routes (individual/company customer) resolve and assign this tenant server-side unconditionally; the browser cannot supply `organization_id`. The pre-existing self-service `/api/auth/register` `org_code` mechanism (client-supplied org UUID, server-validated against `is_active`) is left as-is — it already rejects anything but a real, active org row, and changing it is out of scope here.
- **Separate onboarding flows.** `CreateUserModal`'s single generic agent/customer toggle is replaced, for customers, by two independent routes, Zod schemas and API endpoints — individual vs. company — each imposing its own server-side `role`/`customer_type`/`organization_id`/`reference_code`. Agent/employee creation keeps using the existing modal/route unchanged.
- **Invitation, not admin-visible passwords.** The two new customer onboarding routes use `supabase.auth.admin.inviteUserByEmail`, letting Supabase's own configured mailer deliver the invite; the admin never sees a temporary password. The invite's `redirectTo` lands on the existing `/auth/callback`, then the existing `/settings` → `ChangePasswordForm` lets the invited user set their own password — no new "set initial password" page is built, reusing what already exists. Agent creation's existing direct-password flow (`app/api/admin/users/route.ts`) is unchanged in this phase.
- **Profile area.** Self-service profile management already exists at `/settings` (avatar upload, password change, role-specific fields) — extended in place rather than duplicated into a new `/dashboard/profile`, per the "don't duplicate existing flows" guardrail.
- **Logo storage.** A new `logos` Storage bucket mirrors the existing `avatars` bucket's proven pattern exactly (public read, folder-scoped RLS keyed to `auth.uid()`, one file per user) rather than introducing a new private/signed-URL mechanism — company logos carry the same sensitivity profile as avatars, and reusing an already-reviewed pattern was judged lower-risk than a new one.

## ADR-016: Access and recovery links reach an administrator only on failed email, behind a flag

**Status:** Accepted (owner decision D1 = option C, 2026-11-16). **Context:** audit 2026-11-16, SEC-02; spec REQ-F0-04.

Both customer onboarding routes returned a magic sign-in link on every request, including for accounts that were only linked, and the administrator password-reset route returned the recovery link even when the email had been sent. A link that signs somebody in is a credential; it was travelling through a response body and an administrator's screen by default.

- **Rule.** One pure function, `decideLinkHandoff()` in `lib/link-handoff.ts`, is the only place that decides. A link is returned only when (a) the account was invited or is being recovered, never `link_existing`; (b) the email carrying the link was **not** delivered; and (c) `ADMIN_LINK_HANDOFF` is exactly `"true"`. Otherwise the response carries `email_sent` and a `link_handoff` reason code, and no link.
- **What "email failed" means, per route.** Password reset: `sendEmail()` returned `delivered: false` (no Resend key, or Resend refused). Customer onboarding: `inviteUserByEmail` failed with GoTrue's mail rate-limit code or its "Error sending … email" message (`isInviteEmailFailure`). A successful invite means Supabase Auth accepted the message; later bounces are not observable and are not treated as failure.
- **Onboarding fallback.** GoTrue creates no account when it cannot send the invitation. With the flag on, the route then creates the account through `generateLink({ type: "invite" })` and that invite link is what the administrator may hand over. With the flag off the request fails with 502 and nothing is created. The extra `magiclink` that used to be minted alongside every invitation is gone.
- **Audit.** Every issuance is recorded with actor, target, organization, link type, delivery result and decision — never the link or an address. `hd_ticket_audit_logs` is ticket-scoped and cannot hold an account event, so the record was a structured server log line (`[audit] access link issued`). Since Phase 1 it is stored in `hd_admin_audit_logs` (ADR-020) and the log line remains as a secondary trace.
- **Consequences.** An invited customer who never finishes setting a password is helped through the administrator password reset, not a standing magic link. Without a verified sender domain and with the flag off, a failed recovery email leaves the administrator with a clear failure message and no link — deliberately. The flag is meant for the demo environment and should be `false` when the product is sold.
- **Unverified assumption.** That GoTrue rolls the user back when the invitation mail fails is taken from its documented behaviour, not exercised against the live instance. If a user were left behind, the fallback's `generateLink` fails and the route returns the error unchanged.

## ADR-017: AI quota in PostgreSQL, enforced by a SECURITY DEFINER function

**Status:** Accepted (owner decisions D2 = option A, D4 defaults, 2026-11-16). **Context:** audit 2026-11-16, SEC-01 / SCL-04; spec REQ-F0-02, REQ-F0-03.

`/api/translate`, `/api/ai/wiki-chat` and the `translateText` action accepted any signed-in account on a shared instance, with unbounded input and no rate limit.

- **Gate order.** `requireActiveAiMember` (401 without a session; 403 unless the caller's own `hd_profiles` row has an organization, is not frozen and is not deleted) → Zod bounds (400) → quota (429 with `Retry-After`) → provider. Invalid input never consumes quota.
- **Limits** (`lib/ai/limits.ts`): 30 requests/hour and 200/24 h per user, 1000/24 h per organization, across the three endpoints together; text ≤ 5000 characters; chat ≤ 20 messages and ≤ 12000 characters in total, roles `user`/`assistant` only.
- **Store.** Table `hd_ai_usage` and function `hd_consume_ai_quota` (migration `202611160001_ai_quota.sql`) in the existing database rather than a new Redis service. RLS is enabled with no policies and all privileges are revoked from `anon`/`authenticated`; only `service_role` may execute the function. It counts and inserts under a per-organization transaction advisory lock, re-checks membership, and sweeps rows older than 7 days.
- **Fail closed.** If the function is missing or errors, the endpoints answer 503 and do not call the provider. The migration must therefore be applied before this code is deployed.
- **One translation path.** `translateText` and `/api/translate` share `lib/ai/translate.ts`; the action moved from Sonnet to `claude-haiku-4-5-20251001`. Unsupported locales are now rejected instead of silently translated to English.
- **Trade-offs.** One extra database round trip per AI request; windows are sliding and approximate under clock skew of a single database, which is acceptable at this volume. Revisit with a dedicated store when volume justifies it.

## ADR-018: SLA sweep every five minutes from pg_cron, secret in Vault

**Status:** Accepted (owner decision D5, 2026-11-17: "the most logical option"). **Context:** audit 2026-11-16 SCL-01 / DOM-01; production check 2026-11-17 showed `/api/cron/sla` answering 503 (no valid `CRON_SECRET`), so the daily sweep had never run. Spec REQ-F1-01/02.

- **Schedule.** Vercel Hobby crons run at most daily, too coarse for a one-hour response target. A pg_cron job (`hd-sla-every-5-min`, migration `202611170002`) calls `GET /api/cron/sla` every five minutes through pg_net. The daily Vercel cron stays as a backup.
- **One implementation.** The job calls the existing endpoint instead of re-implementing the SLA rules in SQL, so `lib/sla.ts` remains the only source of truth.
- **Secret.** Read from Supabase Vault (`hd_cron_secret`) each time the job fires; it is not in the migration or in `cron.job`. It must equal `CRON_SECRET` in Vercel (≥ 32 characters).
- **Scale.** The route walks active tickets in keyset pages of 200 within a time budget and stores its cursor in `hd_cron_state`, so a large backlog is completed across runs.
- **Once-only notices.** A partial unique index on `hd_notifications (user_id, ticket_id, type)` for the two breach types makes overlapping runs safe; breaches now also notify every active admin of the organization.
- **Trade-off.** Same exposure level as the existing service-role key on the shared project. Revisit when HelpDesk moves to a dedicated project.

## ADR-019: Local Supabase and CI instead of hosted staging

**Status:** Accepted (owner decision D6-A, 2026-11-17). **Context:** spec REQ-F1-07; Supabase branching needs the Pro plan.

- Developers use `supabase start` / `supabase db reset`; every pull request gets ephemeral PostgreSQL databases in CI where each new migration is applied twice and its pgTAP suite runs.
- The pre-`hd_` bootstrap scripts moved to `docs/legacy/` (do not execute). A HelpDesk-only baseline of the shared production schema is pending (`docs/runbooks/baseline.md`).
- Revisit with hosted staging (branching) when the project has the Pro plan.

## ADR-020: Append-only administrative audit and write lockdown on tickets

**Status:** Accepted (owner decision D7-A, 2026-11-17). **Context:** audit 2026-11-16 SEC-05, SEC-07, SEC-08; spec REQ-F1-04/05/06.

- **`hd_tickets`.** `anon` and `authenticated` lose INSERT/UPDATE/DELETE/TRUNCATE and the write policies are dropped (migration `202611170003`). Every write goes through an API route with `service_role` and explicit tenant predicates; portal ticket creation moved to `service_role` in the same phase and **must be deployed before the migration**.
- **`hd_ticket_audit_logs`.** Append-only for every role: triggers raise `HD001` on UPDATE, DELETE and TRUNCATE, and the privileges are revoked from the API roles and `service_role`. Retention, when required, is an explicit migration that disables the trigger in its own transaction.
- **`hd_admin_audit_logs`** (migration `202611170004`): role changes, user creation, freeze, soft-delete/restore, access-link issuance, customer creation and the PII setting are recorded by `logAdminEvent()` with actor, target, outcome and non-sensitive details. The MCP server writes `ticket.status_changed` with actor type `mcp`. Readable only by admins of the same organization; append-only like the ticket audit.
- **Failure mode.** `logAdminEvent()` never throws to the caller; a failed write is logged with its error code. The action is not rolled back, because refusing an administrative action for an audit outage would block operations; the gap is visible in the server log.
